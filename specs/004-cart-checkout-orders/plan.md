# Implementation Plan: Cart, Checkout & Orders

**Branch**: `vtech-med-v1` | **Date**: 2026-10-09 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/004-cart-checkout-orders/spec.md`

---

## Summary

Implements the full ecommerce transaction flow: guest/auth carts, two-phase checkout (preview + place), order lifecycle management (8 statuses), province-based Canadian tax, concurrency-safe stock decrement, and admin/patient order views.

---

## Technical Context

**Language/Version**: TypeScript 5.x (strict), Node.js 20

**Primary Dependencies**:
- Express.js (routing + middleware)
- Drizzle ORM (queries + migrations)
- `zod` (request validation)
- `jsonwebtoken` (preview token signing)
- `uuid` (cart token generation)

**Storage**: PostgreSQL (Dockerised). New tables: `facility_sequences`, `shipping_methods`, `carts`, `cart_items`, `orders`, `order_items`, `order_status_history`. See `data-model.md`.

**Testing**: Vitest + supertest (`npm test` in `backend/`). Test fixtures: `backend/tests/setup/fixtures.ts`.

**Target Platform**: Linux server / Docker (development on Windows 11)

**Project Type**: REST API module within `backend/src/modules/`

**Performance Goals**: Two-phase checkout must complete under 2s p95 under moderate load

**Constraints**:
- All totals calculated server-side — never trust frontend amounts
- Internal admin `notes` MUST NEVER appear in patient-facing responses
- Stock decrement must be concurrency-safe (SELECT FOR UPDATE)
- Order number generation must be collision-free (SELECT FOR UPDATE on `facility_sequences`)
- Guest carts must use HttpOnly cookies (`medisyn_cart`)
- QST (Quebec) uses additive method (applied on pre-GST subtotal)
- Preview token expires in 15 minutes; server re-calculates totals at placement regardless

**Scale/Scope**: Single-facility ecommerce MVP

## Complexity Tracking

| Design Choice | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| `facility_sequences` table for order numbers | Human-readable sequential order numbers per facility, collision-free | MAX+1 race condition; SEQUENCE can't be easily facility-scoped |
| Two-phase checkout (preview + place) | User must see totals before committing; server re-calculates at placement | Single endpoint doesn't show totals before commit |
| Preview token | Confirm user saw accurate totals before placing (UX flow validation) | Stateless re-entry without confirmation; server never trusts preview token amounts anyway |
| Guest cart (server-side) | Merge on login, cross-device, server-enforced stock | Cookie payload cart grows unbounded and can't enforce stock |

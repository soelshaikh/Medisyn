# Implementation Plan: Async Email & Notification Infrastructure

**Branch**: `007-async-email-notifications` | **Date**: 2026-10-10 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/007-async-email-notifications/spec.md`

## Summary

Replace the current synchronous nodemailer email sends in `src/core/auth/email.service.ts` with a BullMQ-backed async queue. Add eight Handlebars HTML email templates covering all transactional email types. Add a facility-scoped in-app notification system (patient feed, mark-read, broadcast) with Redis-cached unread counts. Add an admin email log with retry capability.

## Technical Context

**Language/Version**: TypeScript 5.6 strict, Node.js 22 (same as existing backend)

**Primary Dependencies**:
- `bullmq` ^5.x — queue + worker (add; Redis already wired via `ioredis`)
- `handlebars` ^4.x — HTML template rendering (add)
- `node-cron` or BullMQ repeatable jobs — appointment reminder scheduler (resolved in research.md: BullMQ repeatable)
- `nodemailer` — already installed, stays as the SMTP transport inside the worker

**Storage**: PostgreSQL + Drizzle (existing); two new tables: `email_log`, `notifications`; one new Drizzle migration (`0006_async_email_notifications.sql`)

**Testing**: Vitest (existing)

**Target Platform**: Linux server (same as existing backend)

**Project Type**: REST API backend module addition

**Performance Goals**: HTTP response time for email-triggering operations unchanged; email delivery < 60s p99; notification list < 200ms p95

**Constraints**:
- Redis is a cache / job store only — PostgreSQL is source of truth (constitution §III)
- Every facility-scoped DB write (notifications) uses `withTenantContext()` (constitution §I)
- Email log `facility_id` is nullable (platform-level system emails have no facility)
- BullMQ worker must handle Redis unavailability gracefully — fall back to synchronous send, log outcome

**Scale/Scope**: Single pharmacy facility at launch; schema supports multi-tenant from day one (RLS on notifications, nullable facility_id on email_log)

## Constitution Check

| Gate | Status | Notes |
|------|--------|-------|
| Tenant isolation via `withTenantContext()` | PASS | All notification DB writes go through `withTenantContext()`. Email log facility_id is nullable (system emails); facility-scoped reads use RLS. |
| No `SET SESSION` / session-level `set_config` | PASS | Worker opens its own `withTenantContext()` per job — transaction-local context only. |
| Redis is cache only | PASS | BullMQ uses Redis as job store (not source of truth). Email log in PostgreSQL is the persistent record. |
| Auth chain unchanged | PASS | `/me` unread_count added via Redis cache + DB fallback; no new auth steps. |
| Audit all security-sensitive ops | PASS | Admin email log access and broadcast notification are permission-checked; broadcast logged to audit_log. |
| No guessing on material requirements | PASS | All decisions in research.md with rationale. |

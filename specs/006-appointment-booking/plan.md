# Implementation Plan: Appointment Booking

## Summary

Build a full appointment booking system for pharmacy services on the MediSyn Express.js backend. Four modules: (1) Vaccine service catalog (admin CRUD, public browse), (2) Availability slot management (STRICT/OPEN capacity, admin-owned), (3) Concurrency-safe patient booking using SELECT FOR UPDATE row locking within the existing withTenantContext transaction pattern, (4) Appointment lifecycle management (cancel, complete, no_show, internal notes, append-only status history). All data is facility-scoped via RLS. Internal notes are structurally absent from patient-facing TypeScript types.

---

## Technical Context

**Language/Version**: TypeScript 5.x (strict)

**Primary Dependencies**: Express.js, Drizzle ORM, Zod (validation), PostgreSQL 16

**Storage**: PostgreSQL + Drizzle ORM. Four new tables: `vaccine_services`, `availability_slots`, `appointments`, `appointment_status_history`. `appointment_status_history` is append-only (REVOKE UPDATE/DELETE).

**Testing**: Vitest (`npm test`)

**Target Platform**: Node.js 20 LTS, Linux server

**Project Type**: REST API module, backend only

**Performance Goals**: Availability query < 100ms p95. Booking (with row lock) < 300ms p95 under normal load.

**Constraints**:
- All DB operations inside `withTenantContext(facilityId, async (tx) => {...})` — no direct `db` imports in services
- SELECT FOR UPDATE on `availability_slots` row for all booking + cancellation operations
- PgBouncer transaction mode compatible (transaction-local set_config only)
- `internal_notes` structurally absent from `PatientAppointmentDetail` TypeScript interface
- `appointment_status_history` rows: REVOKE UPDATE, DELETE at DB level

**Scale/Scope**: Per-facility, per-service availability queries; concurrent bookings serialize on slot row lock.

```typescript
| 'APPOINTMENT_NOT_FOUND'
| 'APPOINTMENT_INVALID_STATUS_TRANSITION'
| 'APPOINTMENT_DUPLICATE_BOOKING'
```

### Permissions (2 new, under 'appointments' platform module)

- `appointments.read` — View appointments, slots, and services
- `appointments.manage` — Full CRUD on services, slots, and appointment status management

### Concurrency Invariant

Every booking or cancellation that touches `booked_count` MUST:
1. Open inside `withTenantContext`
2. `SELECT ... FROM availability_slots WHERE id=$id FOR UPDATE` first
3. Read `booked_count` from the locked row (not a cached value)
4. Only then insert/update appointments and increment/decrement `booked_count`

### Partial Unique Index (migration SQL only — Drizzle schema DSL cannot express this)

```sql
CREATE UNIQUE INDEX appointments_slot_patient_active_unique
  ON appointments (slot_id, patient_id)
  WHERE status != 'cancelled';
```

### Availability Query — OPEN capacity visibility rule

Patient-facing `remaining` = `GREATEST(0, capacity - booked_count)`.
Admin-facing slots show both `capacity`, `openCapacity`, `bookedCount`, and computed `remaining`.
OPEN slots appear as "full" to patients when `booked_count >= capacity` even though admin can still manually book up to `open_capacity`.

### No-Show Cancellation Semantics

`no_show` does NOT decrement `booked_count` (the patient occupied the slot even if they didn't show). Only `cancelled` status decrements `booked_count`.

## Summary

Implement 9 REST auth endpoints on top of the Phase 1 PostgreSQL/Drizzle/Redis foundation. Covers patient self-registration at a facility (with cross-pharmacy account linking), login with session creation, refresh token rotation with theft detection, single/all-session logout, password reset flow, and email verification flow. All auth events are audit-logged per the constitution. Refresh tokens are delivered as HttpOnly cookies; access tokens are returned in response bodies. Email sending is synchronous via Brevo SMTP (nodemailer) in Phase 2; BullMQ async queue is deferred to Phase 7.

## Technical Context

**Language/Version**: TypeScript 5.6 (strict), Node.js 22

**Primary Dependencies**: Express.js 4.x, Drizzle ORM 0.38, argon2 0.41, jsonwebtoken 9.x, ioredis 5.x, zod 3.x, nodemailer (new — Phase 2 only)

**Storage**: PostgreSQL 16 (Drizzle). No new tables. Uses: `users`, `sessions`, `facilityUsers`, `facilityRoles`, `facilities`, `auditLog`. Redis for session revocation fast-path (Phase 1 infrastructure).

**Testing**: Vitest + real PostgreSQL (Phase 1 test infrastructure). New test files under `backend/tests/auth/`.

**Target Platform**: Linux server (Docker). Windows dev environment.

**Project Type**: REST API service (Express.js monolith)

**Performance Goals**: Login < 1s p95. Token refresh < 200ms p95 (Redis fast-path).

**Constraints**: No new DB tables. No new migrations. No microservices. All packages except `nodemailer` already installed.

**Scale/Scope**: Single-tenant-per-request model (multi-facility via RLS). Phase 2 covers auth only — no patient profile, no prescription, no ecommerce.

## Constitution Check

### Pre-Design Gates

| Principle | Check | Status |
|-----------|-------|--------|
| I. Tenant Isolation | Registration uses `withTenantContext(facilityId)` for facilityUsers + facilityRoles; cross-facility user lookup uses `superAdminDb` via `auth-queries.service`. Sessions created via `superAdminDb` (facilityId can be null for super-admins). | ✅ PASS |
| II. Explicit Authorization | Public endpoints (register, login, forgot/reset password, verify email) bypass auth chain. Protected endpoints (logout, logout-all) use full `authMiddleware` chain from Phase 1. | ✅ PASS |
| III. PostgreSQL is source of truth | Sessions in DB. authVersion in DB. Redis used only as fast-path revocation cache. All Redis reads have DB fallback. | ✅ PASS |
| IV. Audit all security-sensitive operations | All 10 auth event types written to `auditLog`. Failed logins write `auth.login_failed`. Super-admin token refreshes use same mechanism. | ✅ PASS |
| V. Phase-gated development | Phase 1 gate tests must be green before Phase 2 begins. Phase 2 gate: all auth tests green + smoke tests pass. | ✅ PASS |

### Post-Design Re-Check

| Principle | Issue | Resolution |
|-----------|-------|------------|
| I. Tenant Isolation | `sessions` table has RLS. Session creation happens inside `superAdminDb` because facilityId may be null (super-admins) and `withTenantContext` requires a non-null facilityId. | CONFIRMED: use `superAdminDb` for session INSERT only. `superAdminQuery()` wrapper writes audit entry first, then opens transaction. |
| II. Explicit Authorization | `/auth/refresh` doesn't use the Bearer auth chain — it reads the HttpOnly cookie and issues a new access token. The session validity check is embedded in the refresh handler itself. | CONFIRMED: refresh endpoint implements its own token validation (cookie → session lookup → hash verify), not via the standard auth middleware. |

No violations. Complexity table not needed.

## Phase 0 Output Summary

See [research.md](research.md) for full rationale. Key decisions:

1. **Refresh token delivery**: HttpOnly cookie (`refresh_token`, SameSite=Lax, Secure in production). Access token in JSON body only.
2. **Email transport**: `nodemailer` + Brevo SMTP (sync). `nodemailer` is the only new package.
3. **Refresh token format**: `crypto.randomBytes(32).toString('hex')` → stored as `argon2.hash(rawToken)` in `sessions.refresh_token_hash`.
4. **Cross-pharmacy linking**: Look up user globally via `superAdminDb`. Require password verification before linking to new facility.
5. **Patient role**: Lazily created per-facility via `INSERT ... ON CONFLICT DO NOTHING` inside registration `withTenantContext`.
6. **authVersion increment**: Only on logout-all and password reset complete. NOT on single-session logout.
7. **Token expiry**: Email verify = 24h. Password reset = 30min (per FR-017).

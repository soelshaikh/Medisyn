# Session: 2026-10-11m — Auth Service Rewrite (Two-Database Architecture)

## Context

Continuation of Task #5 from the enterprise identity architecture design. The vtech-identity DB schema, identity DB connection, and migration script were already built. This session rewrites the auth layer to use two DBs: vtech-identity for all user/session operations, vtech-core for HP/roles/permissions.

  - Session helpers: `createIdentitySession`, `getIdentitySessionById`, `getIdentitySessionRevocationState`, `revokeIdentitySession`, `revokeIdentitySessionOnRotation`, `revokeAllIdentityUserSessions`

## Files Modified

### `backend/src/core/super-admin/auth-queries.service.ts`
- Added imports: `inArray` from drizzle-orm; `healthProfessionals`, `userRoles`, `rolePermissions`, `userPermissions` from `@/db/schema/rbac`; `patients` from `@/db/schema/patient`
- Added `getFacilityByPrefix(prefix)` — query vtech-core.facilities by short prefix
- Added `ResolvedUserAuth` type: `{ healthProfessionalId, facilityId, roles, permissions }`
- Added `resolveHealthProfessionalAuth(userId)` — reads vtech-core:
  1. Gets `healthProfessionals` row by userId (active only)
  2. Gets `user_roles` rows for that HP (active only)
  3. Gets `role_permissions` for all roles → base permission set
  4. Gets `user_permissions` overrides for that HP → applies (granted=false removes, granted=true adds)
  5. Returns merged `{ healthProfessionalId, facilityId, roles[], permissions[] }`
- Added `getPatientFacility(userId)` — returns facilityId from vtech-core.patients (active only)
- Added `createPatientRecord({ userId, facilityId })` — inserts into vtech-core.patients, idempotent

### `backend/src/core/auth/auth.service.ts` — FULL REWRITE
- Removed all imports from `auth-queries.service` (user + session operations)
- Now imports from `identity-queries.service` for all user/session ops
- Imports `resolveHealthProfessionalAuth`, `getPatientFacility`, `createPatientRecord`, `getFacilityBySlug`, `writeAuthAuditEntry` from `auth-queries.service`
- New `JwtPayload` interface: `{ sub, sessionId, accountType, healthProfessionalId, facilityId, facilityPrefix, authVersion, roles[], permissions[] }`
- `register()` — patient self-registration:
  - Checks `facility.prefix` is set (503 if not)
  - Creates user in identityDb with `accountType='patient'`, `facilityPrefix=facility.prefix`
  - Generates unique username via `resolveUniqueUsername`
  - Calls `createPatientRecord` in vtech-core
- `login()` — handles `facility_user` and `patient`:
  - Blocks `super_admin` from facility login route
  - `facility_user`: calls `resolveHealthProfessionalAuth` → verifies HP.facilityId matches request
  - `patient`: calls `getPatientFacility` → verifies match; roles=['patient'], permissions=[]
  - Session created in identityDb
- `superAdminLogin()` — checks `accountType === 'super_admin'` in identityDb
- `refreshToken()` — reads/writes identityDb sessions; no role re-resolution (authVersion bump handles stale roles)
- `logout()`, `logoutAll()` — operate on identityDb sessions; `logoutAll` increments authVersion in identityDb
- `forgotPassword()`, `resetPassword()`, `verifyEmail()`, `resendVerification()` — all use identityDb
- `getMe(userId, facilityId, accountType)` — reads identityDb user + calls `resolveHealthProfessionalAuth` for facility_user

## Decisions — CONFIRMED
- Sessions live exclusively in vtech-identity DB. vtech-core.sessions kept for legacy compat only.
- Refresh token rotation carries existing JWT claims through — no role re-resolution on refresh.
- super_admin accounts cannot log in via the facility login route (`POST /auth/login`); must use `POST /auth/super-admin/login`.
- One user = one facility: if email already exists in identityDb when patient registers at a different facility, they get 409.
